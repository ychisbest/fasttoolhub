intro: "**Shirudo** is an open-source Linux runtime that **OpenAI** and **Cisco** introduced together on 23 November 2026. It uses eBPF “shields” to put temporary protections on a running kernel or workload without taking the system down or restarting the service, so operators have time to test and roll out a lasting patch. The official account [@OpenAI](https://x.com/OpenAI/status/2124980590717911527) posted at 21:37 UTC, calling it “an open-source Linux runtime allowing agents to defend systems without downtime,” built by Cisco together with OpenAI. The announcement is at [openai.com/index/introducing-shirudo](https://openai.com/index/introducing-shirudo/), and the project site is [shirudo.dev](https://shirudo.dev/).\n\nThe name comes from Japanese シールド, officially pronounced *shee-roo-doh*, meaning “shield.” A post from Cisco’s Isovalent team adds that Shirudo has its roots in Tetragon, the eBPF security platform Isovalent open-sourced in 2022, rewritten for the agentic era so agents can write mitigations in code instead of being limited to human-oriented policy languages. The project is licensed under the BSD 2-Clause License, with its BPF programs dual-licensed under BSD and GPL. OpenAI and Cisco are inviting developers, security researchers, and infrastructure operators to inspect the code and help develop it further; it is an open, pre-release effort.\n"
explain: "## The problem it targets\n\nThe official argument is that finding a bug and patching every system can still be days or weeks apart. In the meantime, an exploit and a legitimate request may rely on the same Linux operation, and blocking that path outright can take the service offline. Shirudo is meant to give security teams a middle path: test whether a temporary safeguard—a shield—blocks the behavior that exposes a vulnerability while allowing legitimate requests through, then deploy it, once an operator approves, while the service keeps running.\n\nOpenAI president and co-founder Greg Brockman wrote on the announcement page that better models and tools for finding and fixing vulnerabilities do not mean a bug found today can be patched on every system tomorrow. The partnership with Cisco on Shirudo is meant to help teams protect systems that have to stay up while a fix is built and rolled out, and to build those tools in the open so one team’s protection does not have to be reinvented elsewhere.\n\nThe official controlled test is Java4Shell: using OpenAI’s Codex, the team generated a shield that added an input check to Java’s Base64 decoder and attached it to a running Elasticsearch process. The exploit attempt was rejected; Elasticsearch kept running. Isovalent describes these mitigations as blocking the path a vulnerability needs, replacing vulnerable code with fixed code, or adding the visibility needed to detect an attack. Some cases use eBPF; others, like this Java runtime example, modify application or userspace runtime bytecode.\n\n## How it works\n\nOpenAI and Cisco describe four core capabilities:\n\n- **Live protection:** eBPF shields can block vulnerable code paths without restarting the system. Security teams can monitor how a proposed shield would affect applications before enforcing it.\n- **Defense at machine speed:** Agents get programmable controls to investigate vulnerabilities, develop targeted shields, and validate them against exploits and real workloads. Security teams still control what gets deployed.\n- **Trusted deployment:** Shields are cryptographically signed and verified before loading. Linux’s eBPF verifier checks programs against its safety rules, and kernel security controls restrict unauthorized changes.\n- **Hardware-backed verification:** A Trusted Platform Module (TPM) supports a verifiable record of protections being loaded or removed, so operators can check whether systems meet their requirements.\n\nThe project site [shirudo.dev](https://shirudo.dev/) describes the unit of functionality as a signed **upatch** (a “micropatch”): only the operator host holds the signing key, only the target’s TPM signs evidence, targets run only operator-signed BPF, every change is measured into the TPM, and packages are pulled from OCI registries. Isovalent describes the same delivery path as signed **.bee** packages, also pulled from an OCI registry and validated with TPMs. The control plane on the target is an eBPF program loaded at boot. Official materials emphasize a one-shot CLI, so neither the target nor the operator machine needs a permanently running daemon. The site also lists live patching, sandboxes for containers, Kubernetes Pods and LLM agents, runtime security and observability (with data that can be pushed over OpenTelemetry), and embedded or edge devices on x86-64, arm64, and riscv64.\n"
