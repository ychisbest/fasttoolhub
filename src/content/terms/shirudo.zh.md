intro: "**Shirudo** 是 **OpenAI** 与 **Cisco** 于 2026 年 11 月 23 日共同推出的开源 Linux 运行时：用 eBPF「盾牌」（shield）在系统不停机、服务不重启的情况下，为正在运行的内核或工作负载加上临时防护，好让运维团队有时间测试并滚动正式补丁。官方账号 [@OpenAI](https://x.com/OpenAI/status/2124980590717911527) 在 11 月 24 日 05:37（北京时间，21:37 UTC）发帖介绍，称它是“an open-source Linux runtime allowing agents to defend systems without downtime”，由 Cisco 与 OpenAI 一起打造。官方介绍页是 [openai.com/index/introducing-shirudo](https://openai.com/index/introducing-shirudo/)，项目站是 [shirudo.dev](https://shirudo.dev/)。\n\n名称来自日语「シールド」，官方读音 *shee-roo-doh*，意思是「盾」。Cisco 旗下 Isovalent 的博文还说明，Shirudo 的根子在 2022 年开源的 eBPF 安全平台 Tetragon，并按智能体时代做了重写：让智能体直接用代码编写缓解措施，而不是被限制在面向人类的策略语言里。项目采用 BSD 2-Clause 许可，其中 BPF 程序采用 BSD 与 GPL 双许可，目前仍在邀请开发者、安全研究者和基础设施运维一起完善，属于面向社区的预发布。\n"
explain: "## 它要解决什么问题\n\n官方的判断是：发现漏洞和给所有系统打上补丁，中间往往还有几天甚至几周。这段时间里，漏洞利用和正常请求可能走同一条 Linux 操作路径，如果干脆把这条路径封死，服务也会一起掉线。Shirudo 想给安全团队一条中间路线：先验证一块临时防护能不能挡住暴露点、同时放行合法请求；运维批准后再把它加载到仍在运行的系统上。\n\nOpenAI 总裁兼联合创始人 Greg Brockman 在介绍页上说，给防御者更好的模型和工具，并不等于今天找到的漏洞明天就能补到每一台机器上；和 Cisco 合作 Shirudo，是为了让必须保持在线的系统在修复完成前也能得到保护，并且把这些工具开源，让一家团队找到的防护办法不必被别的团队从头再做一遍。\n\n官方举的受控试验是 Java4Shell：团队用 Codex 生成一块盾牌，给 Java 的 Base64 解码器加上输入检查，并直接附加到正在运行的 Elasticsearch 进程上。攻击尝试被盾牌拒绝，Elasticsearch 本身没有重启。Isovalent 的文章把这类缓解概括为三种动作：堵住漏洞所需的路径、用修好的代码替换脆弱代码，或补上检测攻击所需的可见性；有的场景用 eBPF，有的场景（例如这次的 Java 运行时）则是改应用或用户态运行时的字节码。\n\n## 工作方式\n\n据官方介绍，Shirudo 围绕四项能力设计：\n\n- **在线防护**：eBPF 盾牌可以在不重启系统的情况下阻断脆弱代码路径；安全团队可以先观察拟议盾牌对应用的影响，再决定是否强制执行。\n- **机速防御**：把可编程控制交给智能体，用于调查漏洞、编写针对性盾牌，并对照利用代码和真实负载验证效果；最终部署仍由安全团队决定。\n- **可信部署**：盾牌在加载前经过密码学签名和校验；Linux 的 eBPF verifier 按安全规则检查程序，内核安全控制限制未授权变更。\n- **硬件背书的核验**：借助可信平台模块（TPM）留下防护被加载或移除的可验证记录，供运维核对系统是否符合安全要求。\n\n项目站 [shirudo.dev](https://shirudo.dev/) 把功能单元称为已签名的 **upatch**（micropatch）：只有运维主机持有签名密钥，目标机的 TPM 负责签署证据，目标机只运行运维签过名的 BPF，变更都会被度量进 TPM，并通过 OCI 仓库分发。Isovalent 则把交付包写成签过名的 **.bee** 包，同样经 OCI 仓库拉取并用 TPM 校验。控制平面是开机时加载进操作系统的 eBPF 程序，官方强调采用一次性 CLI，不必在目标机或运维机上常驻守护进程。项目站还列出实时补丁、容器 / Kubernetes Pod / LLM 智能体沙箱、运行时安全与可观测性（数据可经 OpenTelemetry 送出），以及 x86-64、arm64、riscv64 上的嵌入式和边缘设备场景。\n"
