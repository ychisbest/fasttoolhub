intro: "**HogLake** is a **petabyte-scale open table format and lakehouse catalog service** from product-analytics company **PostHog**, made public on **November 2, 2026** with the post *Why we're moving our warehouse off DuckDB*; the code is open source at `PostHog/hoglake` on GitHub.\n\nFive months earlier PostHog had rebuilt its managed warehouse on DuckDB plus DuckLake, but at roughly **2 PB, 1 trillion rows and 15.3 million snapshots**, single-table writes could take over three minutes and catalog statistics kept piling up. PostHog switched to **its own Trino fork plus HogLake**, and new Trino clients now use HogLake automatically."
explain: "## Design highlights\n\n- **Catalog as a service**: all catalog SQL lives server-side behind a REST API; clients never see the metadata database.\n- **Postgres as the only metadata backend**: snapshots, schema evolution, data files and statistics are rows in Postgres, while data lives as **Parquet** in object storage.\n- **Commits scoped to the write set**: one commit is one snapshot, and its cost does not grow with catalog size.\n- **Deletion vectors** for row-level deletes, one live vector per data file.\n- **Server-owned maintenance**: compaction, snapshot expiry and cleanup run as background jobs.\n- **Time travel**, a **changefeed** with consumer offsets, Prometheus metrics and an audit log.\n\n## Compared with DuckLake and Iceberg\n\n| | HogLake | DuckLake | Iceberg |\n|---|---|---|---|\n| Metadata lives in | Postgres, behind a service | An RDBMS read directly by clients | Files in object storage plus a catalog pointer |\n| Who commits | The server | Every client (embedded extension) | Every client (pointer swap) |\n| Engine support | Trino connector, DuckDB extension, Python; Iceberg REST facade designed | DuckDB | Nearly universal |\n\n## Components\n\nA Kotlin/Ktor server, the `pyhoglake` Python client, a DuckDB extension, a React web console and the `hedgerow` replication daemon."
usage: "## When it fits\n\n- Lakehouse teams at **TB-to-PB scale** where DuckLake's single-node or catalog performance is a bottleneck.\n- Architectures that want **metadata centralized in Postgres, with one service committing and maintaining it**, instead of many clients racing.\n- Setups using **Trino** for distributed queries that still want **DuckDB** read/write access locally.\n\n## Getting started\n\n1. Read PostHog's post at posthog.com/blog/moving-off-duckdb for why they migrated.\n2. Clone `PostHog/hoglake` on GitHub and deploy Postgres plus the HogLake server.\n3. Read and write Parquet tables through the Trino connector, the DuckDB extension or `pyhoglake`.\n4. PostHog Cloud users: newly provisioned warehouses (Trino clients) use HogLake automatically, and existing DuckLake catalogs remain supported."
